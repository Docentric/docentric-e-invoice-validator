# Agent Instructions: Docentric e-Invoice Validator

Shared instructions for all AI coding agents (GitHub Copilot, Claude Code, others). This file is the single source of truth; `CLAUDE.md` and `.github/copilot-instructions.md` only point here.

REST API and web UI for validating ZuGFeRD / Factur-X e-invoices (PDF and XML). The backend wraps the Mustang Project CLI (Java) and is used mainly for QA of Docentric AX.

## General Principles

- Keep changes small, focused and in line with existing patterns. No unrelated refactoring.
- Preserve existing behavior and public API contracts (REST contracts, `ErrorCode` values) unless a breaking change is explicitly requested.
- Do not add dependencies unless clearly necessary. Do not change TFM, SDK or `LangVersion`.
- Never invent APIs or Mustang CLI options; verify them in code or documentation.
- Never commit secrets, credentials or personal data. Treat uploaded files as untrusted input.
- Do not edit generated files or build output (`wwwroot/assets/*`, `*.g.cs`, `// <auto-generated>`).
- Do not hand-edit `Mustang-CLI-*.jar`; it is upgraded only as part of a dedicated dependency upgrade.
- Be concise and direct. Write responses and code comments in ASD-STE100 Simplified Technical English.
- Prefer simple, clear solutions over unnecessary abstractions.
- Do not assume. When uncertain, verify or ask.
- Inspect existing code and configuration before making changes.
- Complete requested work end-to-end when practical. Run relevant verification before finishing and clearly report anything that could not be verified.

## Branching Strategy

- `main` is the always-releasable default branch. Never commit directly to `main`; all changes go through a pull request.
- Create one short-lived branch per GitHub issue from the latest `main`.
- Branch name: `<type>/<issue-number>_<short-kebab-case-description>`
  - Types: `feature`, `bugfix`, `hotfix`, `chore`, `docs`.
  - Examples: `feature/17_upgrade-mustang-project-cli-to-2.26.0`, `bugfix/21_fix-pdf-upload-limit`.
  - Work without an issue: `chore/noissue_<description>`.
- Keep branches up to date by rebasing on or merging `main`; resolve conflicts locally.
- Delete the branch after merge.
- Releases are produced from Git tags named `v<SemVer>` (`vMAJOR.MINOR.PATCH`, optionally with a prerelease suffix such as `v1.2.3-preview.0`). The pipeline strips the `v` and passes the result as `/p:Version`, which overrides the placeholder `0.0.0` in `src/Directory.Build.props`.

## Commit Messages

Format: `#<issue> <Imperative summary>`

- Start with the issue number (`#17`). Use `#noissue` when none exists. Multiple issues: `#13, #19, #20 ...`.
- Summary in imperative mood, capitalized, no trailing period, about 72 characters or less (e.g. `#15 Migrate to Tailwind CSS v4 and update utilities`).
- Optional prefixes such as `feat:` / `fix:` after the issue number are acceptable but not required; stay consistent within a PR.
- Add a body (blank line after the subject) when the "why" is not obvious: motivation, trade-offs, breaking changes.
- One logical change per commit; do not mix formatting-only changes with functional changes.

## Pull Requests

- Target `main`. Title follows the commit format: `#<issue> <Imperative summary>`.
- Description must include (the template in `.github/pull_request_template.md` provides these sections):
  1. **Summary**: what and why.
  2. **Related issue**: `Closes #<n>`.
  3. **Changes**: bullet list of notable changes.
  4. **Testing**: automated tests added/run and manual verification (including Docker if relevant).
  5. **Breaking changes / notes**: API, configuration or deployment impact, if any.
- Keep PRs small and focused; CI (`build.yml`) must pass.
- Add or update tests and documentation (README, `ErrorCode.Examples.md`, Swagger metadata) when behavior changes.
- Prefer squash merge with a message following the commit format.
- Address review comments with follow-up commits; do not force-push over reviewed history without notice.

## C# Code Style and Naming

Follow `.editorconfig` first:

- 4 spaces indent, CRLF line endings, file-scoped namespaces, `Nullable` and `ImplicitUsings` enabled.
- Namespace matches folder structure under root namespace `Docentric.EInvoice.Validator.RestServer`.
- One top-level type per file; file name equals type name.
- Naming:
  - Types, methods, properties, events, constants: `PascalCase`.
  - Interfaces: `IPascalCase`.
  - Parameters and locals: `camelCase`.
  - Private/internal/protected fields: `_camelCase`.
  - Async methods end with `Async`.
  - Endpoint groups: `<Area>Endpoints`; DTOs: `<Name>Request` / `<Name>Response`.
- Least-exposure rule: `private` > `internal` > `protected` > `public`. Types default to `internal` unless needed externally.
- Prefer records for DTOs/contracts; prefer immutability.
- Use `var` when the type is obvious; use `sealed` for classes not designed for inheritance.
- Do not add interfaces or abstractions unless needed for external dependencies or testing.
- Null handling: guard early with `ArgumentNullException.ThrowIfNull`, `string.IsNullOrWhiteSpace`; avoid the `!` operator.
- Exceptions: throw precise types; do not catch base `Exception` silently; log and rethrow or return a defined `ErrorCode`.
- Async end to end: accept and pass `CancellationToken`, no sync-over-async, no fire-and-forget, `ConfigureAwait(false)` only in library-style helper code.
- Use dependency injection and `ILogger<T>` with structured logging (message templates, no string interpolation); never log file contents or sensitive data.
- Uploaded files: use `TemporaryUploadedFile`, validate with `FileTypeValidator`, never trust client file names or paths, and always delete temporary files.
- External process execution (Java / Mustang): pass arguments as separate argument-list items (no shell string concatenation), apply timeouts, and capture output.
- Configuration through `appsettings*.json` / environment variables; no hard-coded paths.
- User-facing strings and error texts should be centralized (constants / resources), not scattered.

## Documentation of Public Members

- **Every public type and member** (classes, records, record parameters/properties, methods, properties, enums and enum values, constants, events) must have XML documentation: `<summary>`, plus `<param>`, `<returns>`, `<exception>` and `<typeparam>` where applicable.
- Use `<inheritdoc />` for overrides and interface implementations.
- Comments explain *why*, not *what*. No commented-out code.
- Endpoints should declare Swagger metadata (`WithName`, `WithSummary`/`WithDescription`, `Produces`) consistent with existing endpoints.
- Update `README.md` when setup, features or API behavior change.

## Tests

- Project: `src/Server.Tests`; framework: **xUnit v3** (`[Fact]`, `[Theory]` + `[InlineData]`). Use the framework's built-in `Assert`.
- Mirror source structure: `MustangValidationReportParser` -> `MustangValidationReportParserTests`.
- Test names describe behavior: `WhenReportContainsErrorsThenResultIsInvalid` (or the existing convention in the file).
- Every public test class and public test method (`[Fact]`/`[Theory]`) must have XML documentation: a `<summary>` describing the verified behavior, plus `<param>` for `[Theory]` parameters and primary-constructor parameters (e.g. fixtures). Private helpers need no docs.
- Arrange-Act-Assert, one behavior per test, one logical assertion per test; use `[Theory]` for multiple outcomes of one precondition.
- Do not write tautological tests (tests that cannot fail, or that repeat the implementation logic). They are harmful.
- No conditionals or loops inside tests.
- Test through public APIs; avoid `InternalsVisibleTo` and visibility changes.
- Avoid mocks for code inside the solution; mock only external dependencies (Java process, file system). Prefer small sample XML/report fixtures.
- Avoid disk I/O where possible; if needed use randomized temp paths.
- New or changed public behavior requires tests, including edge cases (empty/invalid input, cancellation, failures) and regressions for fixed bugs.
- Run: `dotnet test src/Docentric.EInvoice.Validator.slnx`.

## Writing Style

Applies to everything written for people: chat answers, commit messages, PR descriptions, review comments, documentation and code comments. Write plainly, specifically and naturally. Prefer complete sentences over slogans, hype, pseudo profundity or dramatic copywriting. These rules override any default tendency toward punchy, inspirational, promotional or thought leadership writing. When in doubt, choose the less theatrical version.

### Punctuation

- Normal hyphens are allowed (compound words, branch names, CLI options, ranges written with a hyphen).
- Do not use em dashes, en dashes or similar characters (horizontal bar, figure dash, minus sign used as a dash, `--` used as a dash) as punctuation or to join clauses. Use a comma, colon, parentheses or a new sentence instead.
- Avoid unnecessary ALL CAPS and excessive rhetorical questions.

### Hard bans

Do not use the contrast formula "It's not X. It's Y." or close variants such as "This isn't X; it's Y.", "Not X, but Y.", "It goes beyond X. It is Y." and "X? No. Y.". Do not use repeated escalation such as "It's not an interview, it's a statement. It's not a statement, it's a revolution." Do not use this structure for emphasis, persuasion, summaries, transitions, headings or punchlines.

### No hype or flattery

- Do not use phrases like "Here is where it gets really interesting", "You have just asked the big question", "This changes everything", "This is the game changer", "This is the moment" or "You are thinking about this exactly the right way".
- Do not call the user unusually insightful, unique, brave, visionary or exceptional unless there is a concrete reason.
- Do not comment on the quality of the user's question.

### Banned headings and transitions

Avoid "Here is why", "Why X matters", "Reality Check" and "Uncomfortable Question". Use headings that name the topic, such as "Trade-offs", "Main constraint", "What changes in practice", "Risks", "Recommendation" or "Evidence".

### No slogan fragments or corporate haiku

- Do not write rhythmic sequences such as "One goal. One team. One winner." or "One team. One mindset."
- Do not write three beat fragments for effect, such as "Faster. Smarter. Better." or "Build. Ship. Win."
- Do not use the exchange formula ("Inputs down, scale up.", "Costs down, value up.").
- Do not use grand metaphors built from a verb and an abstract noun ("Unlock the future.", "Navigate the journey.", "Transform the paradigm."). Name the actual action.
- Do not use the dashboard formula ("Friction gone, growth found.", "Noise removed, clarity gained.").
- Express any useful idea as a normal grammatical sentence, for example "This should save time without reducing quality."

### Preferred style

Prose should be direct, concrete, calm, specific, proportionate to the evidence and free of manufactured drama. Prefer ordinary sentence structure, precise verbs, concrete nouns, explicit trade-offs, measured claims, useful examples and direct answers. Avoid rhetorical inflation, motivational language, fake suspense, forced punchlines, repetitive cadence and poetic business jargon.

### Rewrite rule

Before sending a response, scan for formulaic phrasing. If a sentence sounds like a slogan, manifesto, keynote line, LinkedIn hook, ad headline or corporate poster, rewrite it as ordinary prose.

- Instead of "It's not a feature. It's a platform." write "This feature is broad enough to function as a platform for several workflows."
- Instead of "Friction gone, growth found." write "Removing this source of friction may make growth easier."
- Instead of "One team. One mission. One standard." write "The team should align on a shared mission and a consistent standard."
- Instead of "Here is why this matters." write "The main practical consequence is that deployment becomes cheaper and easier to maintain."

## Security and Performance

- Enforce file type and size limits on uploads; protect against path traversal and zip/PDF bombs.
- Do not expose stack traces or internal paths in API responses; return `ErrorCode` based responses.
- Stream large files; avoid loading whole uploads into memory when not needed.
- Do not optimize without evidence, but avoid obvious scalability problems.
